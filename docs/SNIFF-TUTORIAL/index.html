到底要抓什么包？

一份不跳步骤、不堆术语的图文教程 · 关于 bedrocktool 的 sniff 抓包工具 · 2026-11-14

先把答案给你，一句话

抓的是「服务器发给客户端」的 7 种数据包，也就是服务器告诉你「有人进服了 / 有只羊出现了 / 有个东西掉地上了 / 你被传送了」的那些包。

抓它们只为一件事：数格子。数一数一串字节里到底有没有多出那么 1 个字节、空手到底占 1 格还是 8 格。因为三份说明书互相打架，谁都不能信，只能去数真实服务器发出来的字节。

这 7 个包是：add_player、add_actor、add_item_actor、move_player、mob_equipment、mob_armour_equipment、set_actor_data。第 2 章有中文对照表。

0. 先说清楚：现在还没有真包

⚠️ 最重要的一句：本教程里那几张界面截图（7 帧、100.0%）是程序自测用的假样本，用来验证界面能正常显示，不是真实服务器的抓包结论。别把截图里的数字当成答案抄走。

之前在沙箱里做开发时，没有微软账号、也没有真实的基岩版服务器，所以只跑了造出来的测试数据。真机上到底是不是这样，必须你亲自抓一次包才能定。这就是这次要你做的事。

人话：工具做好了、界面能用了，但「答案」还没填。你现在要去做的，是把真实服务器的包喂给它，让它把三个空填上。

1. 为什么非得抓包

先把背景压成 3 句话

  1. JERCPLD 是个「翻译官」：让老客户端（26.30 / 26.33，协议号 1001）连上新服务器（1.26.40 以上，协议号 2168 / 2193 / 2225）。
  2. 翻译的方式是「按字节改写」：服务器发过来一串数字，翻译官要把它改成老客户端听得懂的另一串数字。差 1 个字节，老客户端就可能看不见别人、看不见掉落物、或者实体直接解析失败。
  3. 现在有 3 个地方不知道该「加」还是「减」字节，因为查到的说明书互相矛盾。猜错就是线上事故，所以只能去看真实服务器到底怎么发的。
图 1：只抓「服务器 → 客户端」这一个方向（红色箭头）。客户端发给服务器的包一律不看，因为三个问题都是「服务器怎么写」。

打个比方：拆快递

服务器给客户端发的是一个个「快递盒」（数据包），里面是一排小格子，每格 1 字节。客户端拿着说明书拆箱：第 1 格是「物品编号」，第 2 格是「数量」……
现在有两本说明书对不上：一本说「如果手里没东西，写 1 格就结束」；另一本说「就算没东西，也要把 8 格全填满 0」。
客户端按错的说明书拆，从第 2 格开始就全错位了。我们不知道服务器按哪本装箱，所以抓一个真盒子，数格子。
人话总结：抓包 = 把服务器发的原始数据录下来，数清楚它到底怎么摆字节，然后照着改翻译代码。不是抓账号、不是抓聊天、不是抓密码。

2. 到底抓哪 7 个包

工具只认这 7 种包，别的包一律跳过（资源包分片之类不关心）。下面这张表就是「抓什么」的完整答案：

包（括号里是编号） 中文意思 游戏里什么时候会发 你要做什么动作把它逼出来
add_player (12)有玩家出现在你视野里另一个玩家进服 / 走到你旁边开两个客户端，或叫朋友进服；让 TA 空手再拿个东西
add_actor (13)生成一个生物刷怪、动物出生、用刷怪蛋控制台或游戏里 /summon sheep 生成一只羊
add_item_actor (15)地上多了个掉落物扔东西、挖掉方块掉落按 Q 扔一个物品到地上
move_player (19)玩家被移动 / 传送传送、重生、被推动用 /tp @s ~ ~10 ~ 把自己传一下

时间线：进服以后照着做一遍

最小验收：其实只要 3 帧

忙不过来的话，抓到下面这 3 帧就能把三个问题全答完：

要抓到的一帧怎么来回答哪个问题
add_player 或 mob_equipment，手里是空的新号空手 / /clear 后让第二人进服悬案 A：空手占 1 格还是 8 格
add_actor 或 set_actor_data，至少 1 条属性/summon sheep / 打一下生物悬案 B：每条属性有没有多 1 字节
move_player，且是传送/tp 一下悬案 C：传送体前面有没有 1 字节开关
建议多抓几帧：工具是投票制，只有「唯一解释」的帧才有投票权。抓 3 帧可能刚好都是歧义帧，结论出不来。抓 20～50 帧更稳，尤其是 mob_equipment（包最短，错一格立刻暴露，是判空手问题最便宜的一帧）。

抓哪个版本的服务器？

要判的是「新版服务器（2168 / 2193 / 2225）到底怎么写」，所以主抓新服务器的包：让代理连一个 1.26.40 以上的 BDS 或服主服。

更严谨的做法是再抓一份老服务器（1.26.30 / 26.33，协议 1001）的包，两边各跑一次工具、对比结论 —— 差异就是要翻译的地方。但只做一次的话，抓新版就够回答问题了。

3. 三个悬案：到底在数哪几个字节

这章是整份教程的核心。看不懂术语没关系，只要看懂「两种摆法差几格」就行。

悬案 A：空手，到底写 1 格还是 8 格？

每个「物品」字段在字节里长这样：物品编号、数量、附加值、是否有网络 ID、方块 ID、附加数据长度。如果编号是 0（空气 / 空手），有两种说法：

图 3：新版用固定 2 字节的「物品编号」，而且没有「空的就跳过」这个捷径；老版读到一个 0 就结束。工具里的词是 air-full（8 字节）/ air-short（短路）。
在界面上怎么看：表格里出现 empty 8B 就是「写满 8 格」；出现 empty 1B / empty 2B 就是「短路」。结论面板里的 air-layout air-full 同理。
为什么要紧：写 JERCPLD 的 item1001To2168 时，如果 air 只写 1 字节，老客户端会把后面 7 个字节全读错。之前写单元测试时就因为这个踩过坑（反向转换少读 6 字节导致整体错位），已经修过一次。

悬案 B：每条「实体属性」有没有多 1 个字节？

实体属性清单（英文叫 metadata）就是一串「这个生物的各项状态」：血量、名字、是否着火、有没有主人……一条一条排着。每一条正常长这样：

图 4：橙色那一格就是争议点。工具里的词是 sel 4/4 —— 4 条属性里 4 条都带这个字节、且都和类型相等。
在界面上怎么看：sel 4/4 / 结论面板 metadata-legacy-type present = 有这个字节；absent = 没有。还有一行 metadata-sanity ... 20/20，是检查「选择子是否都等于类型」，不等就说明这个假设是蒙对的，不算数。
为什么要紧：如果真实格式没有这个字节，翻译时硬插进去，实体包会直接解析失败 —— 玩家看不见生物、看不见其他玩家。这条是三个里最危险的一个。

悬案 C：传送包前面有没有 1 个开关字节？

图 5：橙色 01 就是那个开关。工具里的词是 tp bool=true / teleport-option present。
在界面上怎么看：表格里 tp bool=true = 有开关；结论面板 teleport-option present = 有，absent = 没有。
为什么要紧：多 / 少 1 字节，传送坐标就会读错，老客户端会被传到奇怪的地方或掉线。

顺带也判的两件事（不是主目标）

工具还会顺手判两个小问题，别被结论面板里的陌生词弄晕：

  • item-layout item-instance / item-v1：物品编号是「固定 2 字节」还是「变长压缩」。和悬案 A 一起判。
  • passenger-of-block absent/present：玩家 / 生物包末尾有没有多一段「骑乘方块」的记录。JERCPLD 方案里叫 device_os 的 optionalOnRemaining，属于「不写前缀」的可选字段猜测。
人话总结：三个悬案，本质是三个「差 1 格 / 差 7 格」的数格子问题。抓包的全部意义，就是让真实服务器替我们回答「是」还是「否」。

4. 工具凭什么能下结论

它不猜，也不用任何一份说明书当标准答案。做法是：

1
拿到一帧原始字节，把三个悬案的所有可能组合列出来（比如「8 格 + 有选择子 + 有开关」、「1 格 + 无选择子 + 无开关」……最多几十种）。每一种叫一个假设。
2
用每一种假设，从头到尾把这一帧字节「拆」一遍。拆的时候要求很严：字节不能不够读、不能多出来、数字不能是荒唐值（比如布尔值不是 0/1、选择子不等于类型）。
3
只有一种假设刚好把字节一个不剩地读完 → 它就是答案（有投票权）。两种都行 → 记「歧义」，不投票。一种都不行 → 标红「无匹配」，也不投票。
4
把所有有投票权的帧汇总，按维度出比例。100% 一致才算结论。
图 6：像拼图，只有一种拼法严丝合缝。这样即使说明书全错，也能从字节本身反推出真相。
人话：你不用懂字节怎么拆，工具替你拆完了。你只要看「哪种假设赢了」，以及赢的比例是不是 100%。

5. 手把手操作：离线路线（推荐先做）

为什么先做这条：不用微软账号、不用开服、不用联网，几秒钟出结果。先拿它熟悉界面，再去实时抓真包。

第 0 步：把程序弄出来

git clone https://github.com/fengyushaonian/bedrocktool.git
cd bedrocktool
git checkout feat/packet-sniffer
git submodule update --init --depth 1

子模块（gophertunnel）必须拉，不然编译不过。

编译（三选一，看你的系统）

# Windows（需要 Go + gcc；WinLibs 装完把 bin 加进 PATH）
$env:CGO_ENABLED=1
go build -tags gui -o bedrocktool.exe ./cmd/bedrocktool

# Linux
sudo apt install -y gcc libgl1-mesa-dev libx11-dev libx11-xcb-dev \
  libxkbcommon-x11-dev libxfixes-dev libxcursor-dev libxrandr-dev \
  libxinerama-dev libxi-dev libvulkan-dev libwayland-dev
go build -tags gui -o bedrocktool ./cmd/bedrocktool

# macOS
xcode-select --install
go build -tags gui -o bedrocktool ./cmd/bedrocktool
最容易踩的坑：漏了 -tags gui，编出来就只有命令行版，打开没有图形界面，也看不到 sniff 按钮。带参数启动 = 命令行，不带参数启动 = 图形界面，这是程序原本的规矩。

第 1 步：先弄到一个 .pcap2 文件

离线模式读的是「之前录好的抓包文件」。.pcap2 就是 bedrocktool 自己的录像格式。两种办法弄到：

  • GUI：在设置页选 worlds（或 packs / skins）模式，表单里的 capture 默认勾着，进一次服务器，文件落在 captures/<服务器名>-<时间>.pcap2。
  • 命令行：./bedrocktool capture -address play.example.com:19132
注意：录像里必须包含第 2 章那 7 种包，也就是录像时真的进过世界、生成过生物、扔过东西、传送过。只停在标题界面的录像，抓出来是空的。

第 2 步：启动界面，选 sniff 模式

./bedrocktool        # 注意：后面什么都别加
1
打开后停在 Settings 页，顶部有 4 个模式按钮：packs skins sniff worlds。点中间那个 sniff，它会变成深色（选中）。
图 7：顶部一排紫色小按钮就是模式选择。点 sniff（左数第三个）。这张是「还没选模式」的状态，所以四个都是紫色；选中后 sniff 会变深色（对照图 8 表单页里那个深色的 sniff）。

6. 手把手操作：实时路线（抓真包）

这条才产出真答案。需要：一个真实的基岩版服务器地址 + 一个微软账号（代理要用自己的账号替你连服务器）+ 一个基岩版客户端。
1
GUI 设置页点 sniff，Address 填真实服务器：play.example.com:19132。
2
Listen Address 默认 0.0.0.0:19132。如果本机已经开了 BDS 占了 19132，改成 0.0.0.0:19133，后面客户端也要连 19133。
3
Pcap File 留空，点 Start。页面切到 Sniffer，显示「Waiting for packets」和一句提示，告诉你客户端该连哪个地址。
图 9：等待连接。注意中间那行 Connect your client to 127.0.0.1:19252 —— 以你界面上实际显示的地址为准，截图里是 19252 是因为当时改过监听端口，不是固定值。
4
打开基岩版客户端 → 多人游戏 → 添加服务器 → 地址填界面上显示的那个（同一台机器就填 127.0.0.1 + 那个端口）。
5
首次会弹微软账号登录（代理要拿自己的身份连真服务器）。登录完成后代理才开始转发。顶栏有 Login 按钮可以手动触发。
6
进世界，然后照第 2 章的时间线把动作全做一遍：让第二个玩家进服（空手 + 拿东西各一次）、/summon sheep、按 Q 扔东西、/tp 传送、打一下生物。表格开始一行行冒出来。
7
攒够 20～50 帧后点 Stop → Save report。
成功标志：顶部 packets 在涨、matched 也在涨、unmatched 是 0 或很小；表格里能看到 add_player / add_actor / add_item_actor / move_player 这几种名字。

7. 命令行路线（不想开界面）

功能完全一样，只是没有表格和颜色。两条命令：

# 离线：分析已有的录像
./bedrocktool sniff -pcap captures/server.pcap2 -out sniff.jsonl -max 0

# 实时：代理真服务器，客户端连 -listen 指定的端口
./bedrocktool sniff -address play.example.com:19132 -listen 0.0.0.0:19133 -out sniff.jsonl

# 结果看不懂时加 -verbose，会打印每一种假设拆到哪一步
./bedrocktool sniff -pcap captures/server.pcap2 -out sniff.jsonl -verbose
参数意思
-address要代理的真实服务器；不用 -pcap 时必填
-listen客户端连的本地地址，默认 0.0.0.0:19132
-out每帧一条 JSON 的输出文件
-max最多处理多少帧，0 = 不限
-pcap改成离线分析录像文件
-verbose把每个候选假设都打出来

命令行跑完会额外写 sniff.jsonl.summary.txt；离线模式在录像文件旁边写 <文件名>.verdict.txt。

8. 看结果：什么算成功

图 10：分析完成界面（再次强调：这是自测样本，不是真机结论）。下面按 A / B / C 三块拆给你看。

A 区：顶部四个数字

数字意思希望看到
packets一共探测了多少帧越多越好，≥20
matched 绿色只有一种解释刚好消费完整帧 → 有投票权接近总数
ambiguous 琥珀多种解释都行 → 只计数、不投票越少越好
unmatched 红色没有任何解释能读完 → 版本不对或解析器没覆盖最好是 0

B 区：表格每一行的判定文字

add_player      144   empty 8B · meta 4 · sel 4/4 · instance/full
add_actor        91   meta 4 · sel 4/4
move_player      39   tp bool=true
看到的词人话
empty 8B这帧里的物品是空的，占了 8 字节 → 悬案 A 答「写满」
item 5 8B物品编号 5，占 8 字节
meta 4有 4 条实体属性
sel 4/44 条属性里 4 条都带「选择子」字节，且都等于类型 → 悬案 B 答「有」
instance/full物品是新版固定 2 字节编号布局 + 空栈写满
tp bool=true传送体前面有开关字节 → 悬案 C 答「有」
no match（红）这帧没读通，不算数
ambiguous（琥珀）两种拆法都严丝合缝，不算数

C 区：底部 VERDICT 面板（答案在这）

item-layout            item-instance    4/4 (100.0%)
air-layout             air-full         4/4 (100.0%)
metadata-legacy-type   present          5/5 (100.0%)
teleport-option        present          1/1 (100.0%)
passenger-of-block     absent           3/3 (100.0%)
metadata-sanity        selector byte equals type in 20/20 entries
packets: total=7 matched=7 ambiguous=0 unmatched=0
这一行回答了什么拿到结论后，JERCPLD 代码该怎么改
air-layout air-full悬案 A：空栈写满 8 字节item1001To2168 的 air 分支保持补写尾部字段（现状，别改）
air-layout air-short悬案 A：空栈只写编号就结束改成只输出 li16 的 2 字节，不补尾部
metadata-legacy-type present悬案 B：每条多 1 字节翻译 add_player/add_entity/add_item_entity 时，每条属性在 type 后插 1 字节
metadata-legacy-type absent悬案 B：没有这字节（很可能是文档建模错误）什么都不用加，别自作聪明插字节
teleport-option present悬案 C：传送体前有 bool翻译 move_player 时，mode 为传送就补 01
teleport-option absent悬案 C：没有前缀这个包不用翻译，直接转发
什么算成功：① 三个目标维度都出现；② 每个都是 100.0%；③ matched 占总帧数的大头，unmatched=0；④ teleport-option 至少 1 帧（必须真的 /tp 过）。
不到 100% 怎么办：比如 air-full 12/14，说明录像里混了两个版本的帧，或者某个包还有解析器没覆盖的字段。勾 verbose 重跑，看那 2 帧卡在第几字节；或者干脆重新录一份、只连一个版本的服务器。

输出的文件都在哪

文件内容
sniff.jsonl每帧一条 JSON：包号、长度、判定、事实、十六进制原文、所有候选假设
sniff.jsonl.summary.txt命令行模式的汇总结论
<pcap>.verdict.txt离线模式写在录像文件旁边
sniff-report-<时间>.txt界面里 Save report 导出的，和 JSON 在同一个目录

Output 填相对路径时会落在程序当前工作目录，所以前面才建议填绝对路径。

10. 一页速查卡

贴墙上用

抓什么：服务器 → 客户端的 7 种包（12 / 13 / 15 / 19 / 31 / 32 / 39）。

为什么抓：数格子，解决 3 个「差几个字节」的悬案。

怎么逼出来：第二人进服（空手 + 拿东西）→ /summon → 按 Q 扔东西 → /tp → 打生物。

看哪三行：air-layout、metadata-legacy-type、teleport-option，都要 100%。

拿去干什么：按第 8 章的表改 JERCPLD 的 translateOutboundPacket 里 <2168 分支。

完整操作清单（照着勾）

  • 克隆 feat/packet-sniffer 分支，拉子模块
  • 带 -tags gui 编译（漏了就没有界面）
  • 不带任何参数启动程序
  • 设置页点 sniff
  • 离线：Pcap File 选 .pcap2、Address 留空；或实时：Address 填真服务器、Pcap 留空
  • Output 填绝对路径，Max Packets 填 0
  • 点 Start
  • 实时模式：客户端连界面提示的地址，完成微软登录，进世界
  • 把第 2 章的动作全做一遍（20～50 帧）
  • 点 Stop → 看 VERDICT 三行是否 100% → 点 Save report
  • 把结论按第 8 章的表落到 JERCPLD 代码里，再跑 26.33 / 26.40 / 26.45 / 26.51 / 26.60 回归
